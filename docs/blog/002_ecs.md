# Entity Component System: My Understanding

The simulation needs to model thousands of different things. ECS is how it
stores them.

## 1. The problem

A game world is full of things that share *some* traits but not others.

| Thing | Moves | Attacks | Has health | Drops loot | Other |
|---|---|---|---|---|---|
| Skeleton | yes | yes | yes | bones | |
| Wraith | yes | yes | yes | no | incorporeal |
| Iron ore vein | no | no | yes (pickaxe) | ore | |
| Corpse | no | no | no | player gear | decays |
| Bone construct | yes | yes | yes | bones | summoned |
| The player | yes | yes | yes | no | inventory, skills |

There is no clean taxonomy here. "Lootable" applies to corpses, ore veins and
skeletons. "Summoned" applies to a bone construct but not a lich. "On fire"
applies to literally anything.

Worse, these traits **change while the game is running**. A skeleton catches
fire. The player jumps and is briefly airborne. A summon expires.

---

## 2. The three pieces

### Entity = an ID, and nothing else

```rust
pub struct Entity {
    id: u32,
    generation: NonZeroU32,
}
```

Eight bytes. No data, no methods, no behaviour.

The `generation` counter is there to catch **stale references**.

An entity ID is really a **slot number**, and slots get reused. When something
dies, its slot goes back into a pool, and the next thing that spawns takes it.

Think of hotel rooms. Room 42 frees up, a new guest checks in, and a note
addressed to "room 42" now reaches the wrong person.

Here is the bug that causes:

| Step | What happens |
|---|---|
| 1 | A fireball is cast at the skeleton in slot 42. It stores `target = 42`. |
| 2 | The skeleton dies to something else. Slot 42 goes back in the pool. |
| 3 | A ghoul spawns and is handed slot 42. |
| 4 | The fireball lands and looks up slot 42. |

With only a slot number, step 4 finds the **ghoul** and damages it. A monster
that was never targeted takes a hit, and nothing in the code can tell that
anything went wrong.

The generation counter fixes this. It is a number attached to the slot that
goes up by one every time the slot is reused:

- The skeleton is slot 42, **generation 1**.
- The ghoul that reuses the slot is slot 42, **generation 2**.
- The fireball stored slot 42, generation 1.
- At step 4 the generations do not match, so the lookup returns nothing.

The fireball fizzles, which is the correct outcome. The point is that the
failure is **immediate and obvious** instead of silently hitting the wrong
target, which would be a bug you could never reproduce on purpose.

### Component = plain data, no methods

```rust
pub struct Position(pub Vec2);
pub struct Health { pub current: i32, pub max: i32 }
pub struct Burning { pub damage_per_tick: i32, pub ticks_left: u32 }
pub struct Airborne { pub height: f32, pub vertical_speed: f32 }
pub struct Incorporeal;   // zero-sized: presence IS the fact
```

A component with no fields is a **marker**. It costs nothing and exists purely
so queries can filter on it.

### System = a plain function

`hecs` has no `System` type at all. A system is just a function:

```rust
fn apply_burning(world: &mut hecs::World) {
    for (health, burning) in world.query_mut::<(&mut Health, &mut Burning)>() {
        health.current -= burning.damage_per_tick;
        burning.ticks_left -= 1;
    }
}
```

Read the query as a `WHERE` clause: **every entity that has both `Health` and
`Burning`**. A burning skeleton, yes. A dropped bone, no. No type checks, ever.

## 3. Why not classes or mixins

Inheritance fails immediately: an ore vein takes damage but is not a creature,
and "lootable" cuts across the tree at three different depths.

Mixins are a much better argument. They *are* composition:

```python
class Skeleton(Entity, HealthMixin, MobileMixin, LootableMixin): ...
```

Two things still separate them from ECS.

### Mixins compose at definition time. ECS composes at runtime

A `Skeleton` is a `Skeleton` for life. To set one on fire you must either give
every skeleton a permanent nullable `burning` field, or swap its class at
runtime.

In ECS, changing what an entity *is* means adding or removing data:

```rust
world.insert_one(skeleton, Burning { damage_per_tick: 3, ticks_left: 120 })?;
world.remove_one::<Burning>(skeleton)?;
```

Jumping is the clearest case. `Airborne` exists only while the entity is in the
air. With mixins, either everyone permanently carries height and vertical speed,
or nobody can jump.

### The query runs backwards

Mixins answer *"does this object have Health?"* via `isinstance`.

A game never asks that. It asks the inverse: *"give me everything that has
Health **and** Burning."* With mixins that means scanning every entity in the
world, every tick, for every system.

> Mixins are a full table scan with a `WHERE` clause.
> ECS is an index on those columns.

## 4. How hecs stores it: archetypes

Every entity has a different set of components. That raises a question with no
obvious answer: **how do you physically lay that out in memory?**

Work through it from scratch. Here is a tiny world:

| Entity | What it is | Components it has |
|---|---|---|
| 3 | skeleton | Position, Health, Velocity |
| 7 | skeleton | Position, Health, Velocity |
| 12 | corpse | Position, Loot |
| 19 | ore vein | Position, Health, Loot |
| 24 | skeleton | Position, Health, Velocity |

### Attempt 1: one big table

The obvious approach. One row per entity, one column per component type, and
empty cells where an entity does not have that component.

```text
entity | Position | Health | Velocity | Loot
-------|----------|--------|----------|------
   3   |    p3    |   h3   |    v3    |  --
   7   |    p7    |   h7   |    v7    |  --
  12   |   p12    |   --   |    --    | l12
  19   |   p19    |  h19   |    --    | l19
  24   |   p24    |  h24   |   v24    |  --
```

This works, and it is roughly what a class with optional fields gives you. Two
things are wrong with it.

**Finding things is a scan.** To answer "everything with Position and
Velocity", you must visit every row and check two cells for emptiness. With
10,000 entities that is 10,000 checks, every tick, for every system.

**The empty cells still cost memory.** Entity 12 reserves space for Health and
Velocity it will never use. Add twenty optional component types and most of the
table is empty.

### Attempt 2: one table per combination

Look at the *combinations* that actually occur, rather than the columns:

- Entities 3, 7 and 24 all have exactly (Position, Health, Velocity).
- Entity 12 has exactly (Position, Loot).
- Entity 19 has exactly (Position, Health, Loot).

Three distinct combinations. So make **three separate tables**, one per
combination, and no empty cells anywhere:

```text
Archetype A: (Position, Health, Velocity)
  entities  [  3    7   24 ]

Archetype B: (Position, Loot)
  entities  [ 12 ]

Archetype C: (Position, Health, Loot)
  entities  [ 19 ]
```

**That is all an archetype is: a table for one exact combination of
components.** `hecs` creates them automatically as entities appear, and every
entity lives in exactly one of them.

### Inside one archetype

An archetype still has to store the actual values. Two ways to do it.

**Keep each entity's components together**, so entity 3's position, health and
velocity sit side by side:

```text
[ (p3, h3, v3), (p7, h7, v7), (p24, h24, v24) ]
```

**Or keep each component type together**, one array per type:

```text
Archetype A
  entities [   3    7   24 ]
  Position [  p3   p7  p24 ]
  Health   [  h3   h7  h24 ]
  Velocity [  v3   v7  v24 ]
```

`hecs` does the second one. Its source calls it "one allocation per type".

The arrays line up by position: slot 0 is entity 3, so `Position[0]`,
`Health[0]` and `Velocity[0]` all belong to entity 3. That is how the ECS knows
which values go together without storing an ID next to each one.

This layout has a name, **structure of arrays**, and it is the same idea as a
column store in a database.

### How a query uses this

Now run a system that wants `(Position, Velocity)`.

**Step 1: pick the archetypes.** Which tables have *both* columns? Only A. B
and C are skipped entirely, and none of their entities are ever looked at.

**Step 2: grab the arrays.** Archetype A hands over its `Position` array and
its `Velocity` array.

**Step 3: walk them together**, slot 0, slot 1, slot 2.

The important part is step 1. The filtering happened **once per archetype**,
not once per entity. Three checks, not five. With 10,000 entities spread over
six archetypes, it is still six checks.

That is the difference between an index and a scan, and it is why grouping was
worth the trouble.

### Why iterating is fast

Once you are inside an archetype, three things go right:

- **No gaps.** Every value in the array belongs to an entity that matched. The
  loop never has to skip anything.
- **No checks.** Membership was settled in step 1, so there is no test inside
  the loop.
- **No wasted reads.** Only the two arrays the system asked for get touched.
  Health, loot tables and AI state live in separate arrays and are never read.

The third point matters most. Memory arrives in fixed-size blocks, so reading a
packed array of nothing but positions uses every byte fetched. Reading whole
entity records would drag along every other field with it.

### Looking up one entity

Queries handle "everything that has X". Sometimes you need one specific
entity instead: a fireball's target, the player, the thing you clicked.

For that, `hecs` keeps one more array beside the archetypes. One entry per slot
number, indexed directly by entity ID:

```text
meta table (indexed by entity id)

  id | generation | lives in
  ---|------------|---------------------
   3 |     1      | archetype A, slot 0
   7 |     1      | archetype A, slot 1
  12 |     1      | archetype B, slot 0
  19 |     1      | archetype C, slot 0
  24 |     1      | archetype A, slot 2
```

It is a phone book. An entity ID goes in, and where it actually lives comes
out. Looking up entity 7's health takes four steps:

1. Read `meta[7]`. The ID is the array index, so this is a direct read, not a
   search.
2. Compare generations. The handle says 1, the table says 1, so the handle is
   still valid.
3. Read the location: archetype A, slot 1.
4. Go to archetype A, find its `Health` array, read slot 1. That is `h7`.

Four array reads. No hashing, no scanning.

**This is where the generation counter from section 2 does its work.** When
skeleton 7 dies and a ghoul takes slot 7, the table entry becomes generation 2.
The fireball still holds generation 1, step 2 sees the mismatch, and the lookup
returns nothing instead of returning the ghoul.

**It is also what step 5 of the archetype move updates.** When entity 7 moved
to a new archetype and entity 24 was swapped into the hole it left, both of
their rows in this table had to be corrected:

```text
before   7 -> archetype A, slot 1        after   7 -> archetype D, slot 0
        24 -> archetype A, slot 2               24 -> archetype A, slot 1
```

The meta table is what keeps entity IDs stable while the data underneath them
shuffles between archetypes.

**One caveat.** Being a handful of steps does not make it cheap. Those four
reads land in four unrelated places in memory, so each one can stall waiting
for RAM, and the CPU cannot predict them the way it predicts a sequential
scan. A single lookup costs roughly what several iterated entities cost.

So: iterate when you can, look up by ID only when you must. That is why
`Sim::snapshot` builds its list with a query rather than looping over IDs.

### Why adding or removing a component is slow

Here is the cost of the design. An archetype is *defined* by its exact
component set, so the moment an entity gains a component, it no longer belongs
where it is.

Set skeleton 7 on fire. It has (Position, Health, Velocity) and gains
`Burning`, making it (Position, Health, Velocity, Burning). That is a new
combination, so it belongs in a different archetype:

```text
BEFORE
Archetype A (Position, Health, Velocity)
  entities [   3    7   24 ]
  Position [  p3   p7  p24 ]
  Health   [  h3   h7  h24 ]
  Velocity [  v3   v7  v24 ]

Archetype D (Position, Health, Velocity, Burning)
  does not exist yet

AFTER
Archetype A (Position, Health, Velocity)
  entities [   3   24 ]
  Position [  p3  p24 ]
  Health   [  h3  h24 ]
  Velocity [  v3  v24 ]

Archetype D (Position, Health, Velocity, Burning)
  entities [   7 ]
  Position [  p7 ]
  Health   [  h7 ]
  Velocity [  v7 ]
  Burning  [  b7 ]
```

Five things had to happen:

1. Create archetype D, since no entity had that combination before.
2. Copy `p7`, `h7` and `v7` out of A and into D.
3. Write the new `Burning` value into D.
4. Remove slot 1 from A. Leaving a hole would break the "no gaps" property, so
   the **last** entity (24) is moved into the empty slot instead.
5. Update the records saying where entities 7 and 24 now live, since both
   moved.

So adding **one** component copied **three** others, and disturbed an unrelated
entity as a side effect. An entity with ten components pays ten copies to gain
an eleventh.

Putting the fire out does the same thing again, in reverse.

### The other design: sparse sets

Archetypes made adding a component expensive, because the entity has to move.
So ask the opposite question: **what if entities never moved at all?**

Build that up one step at a time. Take just the `Health` component in our
world. Entities 3, 7, 19 and 24 have it. Entities 12 does not.

#### Step 1: one array indexed by entity ID

The simplest thing that could work. Give `Health` its own array, and put each
entity's health at the index matching its ID:

```text
Health
  index    0    1    2    3    4    5    6    7   ...  19  ...  24
  value    -    -    -   h3    -    -    -   h7   ...  h19 ...  h24
```

Looking up entity 7's health is now instant: read index 7.

But iterating is terrible. To visit every health value you walk the whole
array and skip the empty slots. With 4 entities out of 10,000 having health,
you would read 10,000 slots to find 4 values.

#### Step 2: add a packed array for iteration

Keep a second array holding only the values that exist, back to back with no
gaps:

```text
dense    [ h3   h7   h19   h24 ]
```

Now iterating is fast again. Four values, four reads, no gaps.

But we broke lookup. Entity 7's health is at `dense[1]`, and nothing tells us
that.

#### Step 3: use the first array to point into the second

Change the first array. Instead of holding values, it holds **the index into
`dense`**:

```text
sparse   index   0    1    2    3    4   ...   7   ...  19  ...  24
         value   -    -    -    0    -   ...   1   ...   2  ...   3

dense            [ h3   h7   h19   h24 ]
                    0    1     2     3
```

Read it as: `sparse[7]` is 1, so entity 7's health is `dense[1]`, which is
`h7`.

Now both work. Lookup is two reads. Iteration walks `dense` with no gaps.

#### Step 4: remember who owns each slot

One thing is still missing. While iterating `dense` you know the values but
not which entity each belongs to. So keep a third array alongside `dense`:

```text
dense    [ h3   h7   h19   h24 ]
entities [  3    7    19    24 ]
```

`dense[1]` is `h7`, and `entities[1]` says that belongs to entity 7.

**Those three arrays together are a sparse set.** The name comes from the pair:
a *sparse* array with gaps, pointing into a *dense* array without any. Every
component type gets its own independent set of three, and no entity ever
belongs to a group.

#### Adding a component is now cheap

Set skeleton 7 on fire:

```text
Burning, before        Burning, after
  sparse   (empty)       sparse   [7] = 0
  dense    [ ]           dense    [ b7 ]
  entities [ ]           entities [  7 ]
```

Two writes. Entity 7's Position, Health and Velocity are not touched, and no
other entity is disturbed.

Compare that with the archetype version, which copied three components into a
different archetype and dragged entity 24 into a new slot as a side effect.

#### Removing is cheap too

Take `Health` away from entity 7. It sits at `dense[1]`, and removing it would
leave a gap, which is the one thing `dense` must not have. So the **last**
element is moved into the hole instead:

```text
before   dense    [ h3   h7   h19   h24 ]      sparse[7] = 1, sparse[24] = 3
         entities [  3    7    19    24 ]

after    dense    [ h3  h24   h19 ]            sparse[7] = empty
         entities [  3   24    19 ]            sparse[24] = 1
```

Two moves and two sparse updates. Cheap regardless of how many other
components entity 7 has.

#### The cost: queries wanting several components

This is where sparse sets give something back. There are no groups, so nothing
already knows which entities have both `Position` and `Velocity`. The ECS has
to work it out every time:

```text
Position   dense    [ p3   p7  p12  p19  p24 ]      5 entities
Velocity   dense    [ v3   v7  v24 ]                3 entities
```

1. Start with the smaller one, `Velocity`, and walk its `entities` array:
   `[3, 7, 24]`. That part is a clean sequential scan.
2. For entity 3, jump to `Position`'s **sparse** array at index 3 to find out
   whether it has a position, and where.
3. It says 0, so jump again into `Position`'s **dense** array at index 0 to
   read `p3`.
4. Repeat for 7 and 24.

So: one packed scan, plus **two jumps to unpredictable addresses for every
entity, for every extra component in the query**. Those jumps are what the CPU
is worst at.

Archetypes had already answered "who has both" when the entity was filed, so
they hand over two packed arrays and do no jumping at all.

### Which to use

The trade-off in one line:

> Archetypes pay when an entity's component set **changes**.
> Sparse sets pay when a query wants **several components at once**.

#### What real engines do

| Engine | Storage |
|---|---|
| hecs | archetype only |
| Unity DOTS | archetype (fixed-size chunks) |
| flecs | archetype |
| EnTT (C++) | sparse set |
| bevy_ecs | **hybrid**: archetype by default, sparse set opt-in per component |

The modern answer, and what Bevy settled on, is **hybrid**. You do not pick one
for the whole game. You pick per component type:

```rust
#[derive(Component)]
#[component(storage = "SparseSet")]
struct Bleeding { ... }
```

Bevy's own guidance is worth copying, because it is specific:

- **Default (archetype-style) storage** for components you rarely add or remove
  after spawning. Their example is `Mana`.
- **Sparse set** for components added and removed frequently, or that exist as
  a temporary effect. Their examples are `Bleeding`, a status effect applied
  and later removed, and `CanSeePlayer`, a marker that enemies gain and lose as
  the player moves in and out of sight.

Both of those examples are ARPG mechanics, which is a good sign for us.

#### Applied to Marrowfall

Sort components by **how often the entity gains or loses them**, not by how
often the values change:

| Component | Gained or lost | Wants |
|---|---|---|
| Position, Health, Velocity | never after spawn | archetype |
| Loot, Undead, Incorporeal | never | archetype |
| Burning, Bleeding, Poisoned, Frozen | every few seconds | sparse set |
| CanSeePlayer, InCombat | every few frames | sparse set |
| Airborne | every jump | sparse set |

A skeleton's `Position` changes 60 times a second, but the skeleton never stops
*having* a position, so it belongs in an archetype. `Burning` is the opposite:
the values barely change, but the component appears and disappears constantly.

## 5. What ECS costs

It is not free.

- **Indirection.** There is no `Skeleton` class to open. Behaviour is spread
  across whatever systems query the components a skeleton happens to have.
- **Relationships are awkward.** "This sword is equipped by this player" has no
  foreign keys. You store `Entity` IDs and validate them by hand.
- **The order systems run in changes the result, and nothing warns you.** Say
  there are two systems: `gravity` moves airborne things downward, and
  `collision` pushes anything below the floor back up to floor level.

  Run `gravity` first, then `collision`: gravity moves the player to height
  -0.2, collision notices it is below the floor and puts it back at 0. The
  player lands correctly.

  Run `collision` first, then `gravity`: collision checks the player at height
  0.3, which is fine, so it does nothing. Then gravity moves the player to
  -0.2 and the tick ends. The player is drawn sunk into the floor for a frame.

  Same two systems, same data, different outcome. Neither function mentions the
  other, so nothing in either one hints that the order matters. It is decided
  entirely by whichever function calls them, in our case `Sim::tick`.
- **You cannot restructure the world while iterating it.** The borrow checker
  forbids it. The standard idiom is collect-then-apply:

```rust
let mut landed = Vec::new();
for (entity, air) in world.query_mut::<(Entity, &mut Airborne)>() {
    if air.height <= 0.0 {
        landed.push(entity);
    }
}
for entity in landed {
    let _ = world.remove_one::<Airborne>(entity);
}
```

- **Easy to over-engineer.** For five entity types, a plain `Vec<Monster>` is
  simpler and faster to write. ECS pays off at scale *and* at variety, which a
  crafting sandbox with status effects and summons will definitely have.

## The whole thing in one flow

```text
ENTITY = just an id (u32 + generation)
   |
   |  components attached to it, changing at runtime:
   +-- Position
   +-- Health          COMPONENTS = plain data, no methods
   +-- Velocity
   +-- Burning         <- added when ignited, removed when it stops
   |
   v
SYSTEM = a plain function that asks for a combination

   world.query_mut::<(&mut Health, &Burning)>()
   |
   +-- hecs jumps straight to the matching archetypes
   +-- iterates contiguous arrays (structure of arrays)
   +-- never touches entities that do not match
```
